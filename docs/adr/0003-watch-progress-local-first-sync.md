# Watch Progress is kept on the device and synced to Convex once per viewing

Watch Progress lives on each device (MMKV on mobile, `localStorage` on desktop), and that local copy is what the device trusts. The player saves locally as often as it likes: on pause, on leaving the player, on going to the background, and every 60 seconds while playing. Convex gets one push per viewing, when the user leaves the player or the app goes to the background. It goes into a separate `watchProgress` table, one record per video. On launch and on returning to the foreground, each device makes one one-shot request for records changed since its last fetch. If the device and server disagree, the record saved more recently wins. A push that fails is marked as not yet sent and retried at the next fetch.

The reason is free-plan bandwidth, not function calls. The library screens hold live Convex subscriptions to lists of videos. Any write to a `videos` record makes every list containing it re-run and resend in full, descriptions included, which is about 1.5 MB for a 500-video list. Writing progress there on every pause would use up the free plan's bandwidth within a month. A separate table that nothing subscribes to, plus one-shot reads instead of `useQuery`, keeps the cost to about one small mutation per viewing and one small query per launch. Single-user, last-write-wins, one-record-per-video sync has nothing to merge.

We rejected three alternatives. Progress as fields on `videos` (reactive fan-out, above). Convex as the only store with frequent saves (same fan-out, and nothing to resume from while offline). Local only (progress wouldn't move between the iPhone and the Mac, and adding sync later would mean migrating every device's data).

For the same reason `markOpened`, which patched `videos.lastOpenedAt` on every open while nothing read the field, now does nothing. The apps no longer call it, and it stays only so older installed builds don't fail. Don't add frequent writes to `videos` records.
